# ReadyLoans — Architecture Decision Records (Canonical)

**Status:** Accepted. **Date:** 2026-07-21 (amended 2026-07-23 with owner decisions: clean-start launch, cost ramp, admin-managed pricing, model-agnostic AI, connector framework, VIN decode, Tailwind Plus removal + Stitch-first design selection, blue-green deploys, AI error assistant; **amended 2026-07-24 with owner decision: Supabase → Amazon RDS for PostgreSQL — single-vendor AWS, VPC-private; S3 + sharp/CloudFront for files/images, Socket.IO + Redis as primary realtime, ephemeral-container CI migration dry-runs**). **Owner:** Chief Architect.
**Scope:** Every downstream spec, plan, and implementation document MUST conform to these ADRs. Deviations require a superseding ADR in this file.
**Context:** ReadyLoans evolves the single-store Kia Mont-Laurier Deal Tracker (React 18 + Vite, Express, Supabase Postgres) into a production-grade, multi-tenant, white-label dealership platform (CRM/DMS) plus an AI lead-automation layer, Canada/Quebec-first (Bill 96, Law 25, CASL, PIPEDA). The audit verdict on the current codebase (security 1/10, tenancy 1/10, money 2/10) mandates a strangler rebuild that preserves the feature logic (7/10) as the asset.

---

## ADR-001: Language & Monorepo — TypeScript everywhere, pnpm + Turborepo

**Decision:** Single monorepo: **TypeScript 5.9 (strict) everywhere**, **pnpm workspaces + Turborepo** for task orchestration/caching. Layout:

```
readyloans/
  apps/web            # React SPA (staff platform)
  apps/api            # Fastify core API + WS gateway
  apps/workers        # BullMQ workers (jobs, AI pipeline, drips, crons)
  apps/intake         # Lead-intake edge service (webhooks + ADF/XML)
  packages/db         # schema, migrations, generated types, RLS policies
  packages/contracts  # ts-rest + Zod API contracts (→ OpenAPI)
  packages/schemas    # shared Zod domain schemas & enums (single source of truth)
  packages/core       # domain logic: tax, desking math, commissions, pipeline rules
  packages/ui         # shadcn-based component library + tenant theming
  packages/i18n       # shared EN/FR resources (client + server)
  packages/ai         # Claude agent: prompts, tools, extraction, compliance guards
```

**Alternatives:** JS status quo; Nx; polyrepo. **Rationale:** shared Zod schemas/enums kill the status-vocab and dollars-vs-cents drift documented in the audit; Turborepo is the 2026 default with lower ceremony than Nx. **Consequences:** all current JS is ported, not patched; `packages/core` is where the (valuable) desking/tax/commission math lives once, tested, shared by client and server.

## ADR-002: Frontend — React 19 + Vite 6 SPA, TanStack Query v5

**Decision:** Stay a **Vite SPA**, upgrade to **React 19**, **react-router v7**, **TanStack Query v5** for all server state; no direct database queries from the browser (the legacy DeskingPage direct-Supabase anti-pattern is banned). All data flows through the versioned API using the `packages/contracts` client.
**Alternatives:** Next.js App Router; Remix. **Rationale:** the product is a logged-in, data-dense B2B tool — SSR/SEO adds cost without benefit; the team already knows Vite+react-query; research confirms "Next frontend" is only warranted for public marketing sites (which can be a separate tiny Next/Astro app later).
**Consequences:** one SPA serves all tenants (white-label at runtime, ADR-018); anonymous public pages (credit-app forms) are separate lightweight routes on the same SPA or the intake service.

## ADR-003: API — Fastify v5, versioned REST, ts-rest contracts + OpenAPI 3.1

**Decision:** Replace Express with **Fastify v5**. All endpoints defined contract-first in **ts-rest** with **Zod** schemas (ADR-016), mounted under **`/api/v1`** (URL versioning; breaking changes → `/v2`, old version supported ≥6 months). **OpenAPI 3.1** generated from contracts and published for integrators. Internal app client consumes the typed ts-rest client (tRPC-grade type safety without a second protocol).
**Alternatives:** NestJS (heavier, cold-start cost, DI ceremony); Hono everywhere (edge-first, weaker plugin ecosystem for long-lived servers); tRPC (no external-consumer story). **Rationale:** Encore 2026 comparison — Fastify is the lowest-friction Express upgrade with 2–3x throughput and schema-driven serialization; ReadyLoans has mandatory external surfaces (lead providers, telephony, dealer groups) so OpenAPI REST is non-negotiable.
**Consequences:** every route gets Zod-validated input/output; the ~150 unauthenticated legacy endpoints are not migrated as-is — each is re-created behind auth + tenant scoping (ADR-006/007).

## ADR-004: Realtime — Socket.IO 4 + Redis adapter (ElastiCache Valkey) as primary *(amended 2026-07-24)*

**Decision:** **Socket.IO 4 + @socket.io/redis-adapter on ElastiCache Valkey** (ADR-010/014) running on the Fastify API nodes is the **primary realtime layer**: tenant-namespaced rooms (`tenant:{id}:...`), **authenticated joins** (Better Auth session verified on connect; room membership authorized by the same membership logic as the API), deal-board/lead-queue updates and the F&I live-analysis panel as **events emitted from the API/worker layer on writes** — no database change-capture dependency. Agent online/presence via Socket.IO connection state + heartbeats backed by Valkey (replaces the 60s-heartbeat polling spec). ALB WebSocket support with target-group stickiness; the Redis adapter fans out across API tasks.
**Alternatives:** **Supabase Realtime (the previous primary, superseded 2026-07-24 with the Supabase exit — ADR-008)**; Ably/Pusher (per-message pricing, data residency questions). **Rationale:** Socket.IO + Redis was already the documented escalation path — promoted to primary when the owner chose single-vendor AWS; app-emitted events are explicit, testable, and carry exactly the payload the UI needs (change-capture leaked raw rows); the adapter pattern is the 2026 standard for multi-node WS.
**Consequences:** realtime authorization is enforced at join/emit time by application code — RLS no longer implicitly filters the stream, so **emitters must scope every payload by tenant** (a lint-guarded helper in `packages/contracts` wraps all emits); AI chat token streaming to the agent console uses SSE from the API or the same socket, not a bespoke WS layer; writes that skip the API/worker layer produce no events — banned anyway (ADR-002).

## ADR-005: Webhooks — inbound (JSON + ADF/XML) and outbound (HMAC-signed)

**Decision:** **Inbound:** `apps/intake` exposes per-tenant endpoints `/in/v1/leads/{tenantSlug}/{sourceKey}` accepting JSON (Fluent Forms, Meta/Zapier, OEM) and **ADF/XML**; plus an **inbound-email parser** (Resend Inbound) for ADF-by-email (AutoTrader.ca, Kijiji Autos) and delivery-photo emails. Intake only validates, normalizes to a canonical Lead envelope, records the CASL consent basis (implied-inquiry, 6-month expiry), and enqueues to BullMQ — sub-100ms ACK, at-least-once processing, dedupe by deterministic job ID (provider ID or payload hash). Provider signatures (Meta `X-Hub-Signature-256`, Twilio signature) verified; per-source shared secrets otherwise.
**Outbound:** platform webhooks (deal.stage_changed, lead.created, etc.) signed **HMAC-SHA256** over `{timestamp}.{body}` in `X-ReadyLoans-Signature` with `X-ReadyLoans-Timestamp` (±5 min replay window), per-endpoint secrets with dual-secret rotation, BullMQ delivery with exponential backoff (max 24h) and DLQ, delivery log UI per tenant.
**Rationale:** ADF/XML is the universal automotive interchange format — mandatory; current webhooks have zero signature checks (audit finding). **Consequences:** speed-to-lead SLA (<60s first AI touch) is measured from intake ACK.
**Amended 2026-07-23 (connector framework):** intake is a **generic, configuration-driven connector framework**, not a fixed set of hand-coded parsers. Every lead source is a connector definition — data, not code: transport (JSON webhook, ADF/XML email via Resend Inbound, or API polling), field mappings to the canonical Lead envelope, auth/signature scheme, dedupe key, and consent basis. All currently known lead sources ship as built-in connector definitions, and **any new lead source can be added later through configuration alone**.

## ADR-006: Auth — Better Auth 1.3+ (self-hosted) with the Organization plugin

**Decision:** Adopt **Better Auth v1.3+** as the single auth stack, replacing Supabase Auth: email/password + OAuth, **organization plugin** (orgs, teams, invitations, custom roles/permissions), session management with **short-lived access context + rotating refresh**, per-tenant session revocation, MFA (TOTP) required for owner/gm/admin roles. Cookies: **HTTPS-only, `Secure`, `HttpOnly`, `SameSite=Lax`**, domain-scoped for custom tenant domains. RBAC: the 10 platform roles (owner, gm, sales_manager, used_car_manager, fi_manager, salesperson, wholesale_manager, logistics, admin_office, bdc_agent) modeled as Better Auth roles with a permission matrix in `packages/schemas`; **memberships** = (user, organization, store, roles[]) — additive multi-role, users can span stores/orgs (Hassan's staff span Kia ML / ReadyCar / Riverside). SSO: Better Auth SAML/OIDC package when a dealer group demands it; **WorkOS ($125/connection)** is the buy-option fallback. **Auth0 rejected** (cost).
**Alternatives:** keep Supabase Auth + custom claims hook (no native org model, stale-JWT claims problem); Clerk (org UI but no SCIM, add-on pricing). **Rationale:** research brief names Better Auth 1.3 the 2026 go-to for white-label B2B — orgs/teams/RBAC/SAML with zero per-MAU fees, data in our own Postgres.
**Consequences:** legacy localStorage `kia_user` fallback and passwordless `/users/login` are deleted; auth tables live in our Postgres *(amended 2026-07-24: "our Postgres" is now Amazon RDS per ADR-008 — Better Auth was never Supabase-dependent, so the owner-reconfirmed auth stack is unchanged by the Supabase exit; its tables simply live in RDS)*; permission changes take effect immediately (DB-backed sessions, no stale-JWT window).

## ADR-007: Multi-tenancy — shared schema + tenant_id + forced RLS; Platform → Organization → Store

**Decision:** **Shared schema, `tenant_id` (= organization) + `store_id` on every business row, Postgres RLS ENABLED + FORCED on all tenant tables.** Hierarchy: **Platform → Organization (dealer group, e.g., Hassan Group) → Store (rooftop: Kia Mont-Laurier, ReadyCar, Riverside)**. Tenant context set per-request via `SET LOCAL app.tenant_id / app.user_id / app.store_ids` inside a transaction (pooler-safe); policies read `current_setting(...)`, use `SECURITY DEFINER` membership helpers, and every policy column carries a composite index `(tenant_id, ...)`. App-level scoping middleware remains the first line; RLS is the backstop — **`USING(true)` policies are permanently banned**. Cross-tenant reads (AI network routing, platform admin) go through a small set of audited service-role functions only. Cost-field visibility (cross-store inventory) is app-level column masking, not RLS.
**Alternatives:** schema-per-tenant (catalog bloat, N-migration pain); DB-per-tenant (reserved as Neon-branch escalation for a compliance-demanding enterprise group). **Rationale:** 2026 consensus (PlanetScale/ClickHouse) — shared schema is the B2B default at dozens-to-hundreds of tenants; the network lead-routing feature *requires* cheap cross-tenant queries. **Consequences:** the greenfield schema carries tenancy from day one; *(amended 2026-07-23)* org=Hassan Group and its three stores are provisioned fresh at tenant onboarding — no legacy data backfill (clean start, ADR-026).

## ADR-008: Database — Amazon RDS for PostgreSQL 16 (ca-central-1), VPC-private, RDS Proxy pooling *(amended 2026-07-24; supersedes Supabase)*

**Decision:** **Amazon RDS for PostgreSQL 16 in `ca-central-1`** (Canadian data residency — Law 25 cross-border PIA avoidance), **VPC-private**: no public accessibility, security-group ingress only from the ECS task security groups (ADR-014 networking), **gp3 storage encrypted with KMS**, **deletion protection on**, **automated backups + point-in-time recovery**. Credentials in Secrets Manager (never in the repo).
**Cost ramp (mirrors ADR-014):** *Build phase* — local **Docker Postgres** for dev (**$0**) + one **db.t4g.small Single-AZ** staging instance ($0.0350/hr ≈ **US$26/mo** + 20 GB gp3 @ $0.127/GB-mo ≈ $2.50 → **~US$28–30/mo all-in**; no proxy, no Multi-AZ pre-launch). *Production launch* — **Multi-AZ db.t4g.medium** ($0.1410/hr ≈ US$103/mo) + **RDS Proxy** for connection pooling (replaces Supavisor; ca-central-1 $0.016/vCPU-hr × 2 vCPU ≈ US$23/mo) + gp3 Multi-AZ ($0.254/GB-mo; 50–100 GB ≈ $13–25) + backup storage beyond the free 100%-of-provisioned allowance ($0.105/GB-mo; ~$0–5 early) → **production DB line ≈ US$140–170/mo**. A **Multi-AZ db.t4g.small** ($0.070/hr ≈ $51/mo; line ≈ US$90/mo) is the documented cheaper launch option if load testing permits. **Read replica** added only when reporting load demands it (reports/AI analytics route to replica). Monitoring: **CloudWatch + Performance Insights** (free 7-day retention tier at launch).
**Pooling:** RDS Proxy in front of the instance for API/workers — `SET LOCAL` tenant context per transaction is transaction-scoped and proxy-safe (ADR-007 unchanged: vanilla Postgres RLS, forced, with the typed query layer in `packages/db` setting context) — plus a small direct-connection pool for migrations/LISTEN. **Partitioning:** none at launch; monthly range partitions pre-planned for `messages`, `activity_events`, `notifications` when they exceed ~10M rows. **Indexing strategy:** composite `(tenant_id, <hot column>)` on every table; partial indexes for active-pipeline queries; GIN for tsvector search and JSONB; covering indexes for the kanban board query. Migrations: plain SQL migrations in `packages/db`, forward-only, CI-applied; dry-runs in ephemeral Postgres containers per ADR-023.
**Alternatives:** **Supabase Postgres (the previous decision, superseded 2026-07-24)** — the owner chose **single-vendor AWS + VPC-private networking**; RDS was already the documented exit path (ADR-014), now taken **before build starts, so migration cost is zero** — no data, code, or cutover to migrate. Supabase's bundled services move to the already-documented fallbacks: Realtime → Socket.IO + Redis (ADR-004), Storage/Images → S3 + sharp + CloudFront (ADR-013), DB branching → ephemeral containers + snapshot restores (ADR-023). Neon (better branching; noted, not needed); Aurora (cost/complexity unwarranted at this scale).
**Cost delta:** previous Supabase line was ~$25–75/mo. New line: build phase ~$28–30/mo (within the old range); production ~$140–170/mo (**+~$95–115/mo**) — total production envelope restated in ADR-014 (**~$750–$1,100/mo**).
**Consequences:** the JS `SERVICE_ROLE_KEY`-everywhere pattern dies — there is no service-role key at all; workers/admin functions use scoped DB roles with credentials from Secrets Manager. The database is unreachable from the public internet; developer access is via bastion/SSM port-forwarding only.

## ADR-009: Data conventions — integer cents, soft delete, audit events

**Decision:** Platform-wide invariants (from the Guardrails doc, now canonical): all money = **INTEGER cents** (no exceptions — fixes the $1,500-pad-as-$15 class of bugs); tax stored per-deal as split components (`gst_cents`, `qst_cents`, `pst_cents`, `hst_cents`) written back from the desking engine, never recomputed from a single blended rate; **soft delete** (`deleted_at`) on all business tables; every state change emits an `activity_events` row (append-only, tenant-scoped); all FKs real (salesperson-by-ILIKE-name matching is banned — `deals.salesperson_id → users.id`); one status vocabulary per entity defined in `packages/schemas` (legacy duplicates `deal_status`/`finance_status` are simply not carried forward — one vocabulary from day one; *amended 2026-07-23*, clean start per ADR-026); UTC timestamps, tenant timezone applied at render; generated columns must be immutable (no `CURRENT_DATE`/`NOW()` — computed in views or queries).
**Rationale/Consequences:** eliminates the audit's money-unit drift, enum drift, and duplicate-state findings at the type level; commission engine reads/writes cents only.

## ADR-010: Caching — Redis-protocol Valkey (managed), typed cache layers

**Decision:** One managed **Valkey 8 / Redis-compatible** instance (provider per ADR-014 topology; TLS required) serving: (L1) per-process in-memory LRU for hot config (tenant branding, feature flags, 30–60s TTL); (L2) Valkey cache for session lookups, tenant/branding records, inventory summaries for the AI agent, rate-limit state, BullMQ. Cache keys always tenant-prefixed (`t:{tenantId}:...`); explicit invalidation on write for branding/config, TTL elsewhere. **Upstash Redis** only if an edge deployment of `apps/intake` needs HTTPS Redis.
**Alternatives:** pg-boss/Postgres-only (viable <100 jobs/s but forfeits rate-limit + cache uses). **Rationale:** research — managed Valkey in-VPC for long-lived Node + BullMQ; Upstash cost-cliffs past ~1M commands/day. **Consequences:** no correctness-critical data lives only in cache; Valkey loss degrades performance, never consistency.

## ADR-011: Rate limiting — token bucket in Valkey, layered, tenant-aware

**Decision:** **Token bucket** implemented with atomic Lua via **`rate-limiter-flexible`** on Valkey, enforced in Fastify onRequest, layered narrowest-wins: (1) global infra ceiling, (2) per-IP (esp. unauthenticated intake/auth endpoints), (3) **per-tenant quota** (plan-tier-based — white-label plans map to quotas), (4) per-endpoint for expensive paths (PDF/Excel export, AI call initiation, bulk imports). `429` + `Retry-After` + `X-RateLimit-*` headers. Webhook intake gets high-burst buckets; auth endpoints get strict brute-force limits.
**Rationale:** research — no rate limiting exists today; noisy-neighbor error spikes of 40–60% without tenant quotas. **Consequences:** per-tenant quota config lives on the tenant record; AI usage limits double as billing meters (ADR-024).

## ADR-012: Background jobs — BullMQ 5 on Valkey

**Decision:** **BullMQ 5** in `apps/workers`: queues for email, SMS, AI-conversation turns, voice-call orchestration, PDF/Excel generation (sandboxed workers), webhook delivery, image processing, drip engine, and the **lead pipeline as a BullMQ Flow** (intake → normalize/dedupe → consent check → AI first-touch → extraction → routing → agent assignment). Rules: **idempotent jobs with deterministic IDs** (webhook redelivery dedupe), exponential backoff, **DLQ per queue** with alerting, `removeOnComplete/Fail` TTLs, `tenant_id` in every payload, per-tenant group limiters so one dealership's bulk import can't starve others. **Cron/scheduled work** (6 daily checks, drip enrollment at 10:00 tenant-local, 15-min task-overdue sweep, DNCL freshness, report schedules) = BullMQ repeatable jobs — replaces the currently nonexistent scheduler that left specs' automations inert.
**Alternatives:** pg-boss; Inngest/Trigger.dev (vendor lock, data residency questions). **Consequences:** nothing slow or side-effecting runs inline in a request handler (emails/PDFs currently do — banned).

## ADR-013: File storage & images — Amazon S3 private buckets + sharp pre-generated variants + CloudFront *(amended 2026-07-24)*

**Decision:** **Amazon S3 in `ca-central-1`** — private buckets (Block Public Access on, SSE-KMS encryption), per-tenant path prefixes `tenant/{id}/...`, **presigned URLs only** for both upload and download (the legacy anon-writable bucket pattern stays banned); access enforced by the API (tenant scoping) issuing short-lived presigned URLs. Uploads pass a **sharp** step in workers: EXIF/GPS strip, max-dimension enforcement, blurhash/LQIP generation, optional dealer watermark (unchanged) — and now also **pre-generate WebP/AVIF variants at the `srcset` breakpoints**, stored alongside the original and **served via CloudFront** (already in-stack, ADR-14; origin access control to the private bucket). **Cloudflare Images stays the documented fallback** if on-the-fly transforms/smart-crop ever become a requirement. Document files (contracts, IDs, credit apps) live in a separate bucket class with stricter access, object lock/retention policies, and no CDN caching.
**Alternatives:** **Supabase Storage + Image Transformations (the previous decision, superseded 2026-07-24 with the Supabase exit — ADR-008)**; on-the-fly Lambda/CloudFront image resizing (cold-start + per-request cost for a bounded, predictable variant set). **Rationale:** single-vendor AWS; the workload is inventory photos with a fixed set of 6 angles and known breakpoints — pre-generation is cheap (sharp compute already budgeted in workers), cacheable forever (immutable variant keys), and avoids per-transform pricing. **Consequences:** accepted variant sprawl for the bounded breakpoint set; adding a breakpoint is a backfill job; vehicle photos remain the main workload (6 required angles per unit); S3 storage/egress at pilot scale is a few US$/mo (egress via CloudFront's free tier ≈ $0).

## ADR-014: Hosting topology & load balancing — AWS `ca-central-1` (Montreal)

**Decision:** All platform compute runs on **AWS in `ca-central-1` (Montreal)** — owner decision, superseding the earlier Railway/Vercel topology.

- **SPA:** static assets in **S3**, served by **CloudFront** (TLS 1.3, HTTP/3, compression). Certificates via **ACM** (auto-renewed). **Per-tenant white-label custom domains** terminate on CloudFront with per-domain ACM certs — adopt the **CloudFront SaaS Manager / multi-tenant distribution** model as the tenant-domain count grows (one distribution config, per-domain certs, no distribution sprawl); DNS-validated ACM issuance is the tenant onboarding step.
- **API / workers / intake:** Docker images in **ECR**; **ECS Fargate** services — `apps/api` **minimum 2 tasks spread across 2 AZs**, `apps/workers` scaled on BullMQ queue depth (custom CloudWatch metric), `apps/intake` as its own small service — behind one **Application Load Balancer** (HTTPS only, TLS 1.3 security policy, HTTP→HTTPS redirect, health-checked target groups, host/path routing `api.` / `in.`). Target-tracking auto-scaling (CPU + ALB request count for API). **ARM64/Graviton images preferred** (~20% cheaper than x86 Fargate).
- **Cache/queues:** **ElastiCache for Valkey** in-VPC with TLS (satisfies ADR-010/011/012): `cache.t4g.micro` single node at pilot (Valkey loss degrades performance, never consistency — ADR-010), replica/Multi-AZ added before GA; ElastiCache Serverless is the alternate if usage stays tiny.
- **Networking:** one VPC, 2 AZs — public subnets (ALB, NAT) + private subnets (Fargate tasks, ElastiCache); least-privilege security groups (ALB→api only, tasks→Valkey only). Free **S3 gateway endpoint**; **single NAT gateway at pilot** (~$39/mo — accepted cost and single-AZ egress risk; second NAT and ECR/CloudWatch/Secrets **interface endpoints** added only when NAT data-processing charges justify them — the ~$7/mo-per-endpoint-per-AZ math rarely wins at pilot scale).
- **Edge security:** **AWS WAF** on both CloudFront and the ALB (AWS managed core rule sets + rate-based rules; complements, not replaces, app-level limits in ADR-011).
- **Secrets:** **AWS Secrets Manager** injected into task definitions; **KMS** already in-stack for field-level encryption (ADR-015 unchanged). **DNS:** **Route 53**.
- **Database/Storage/Realtime** *(amended 2026-07-24 — the Supabase exit path was taken before build start)*: **Amazon RDS for PostgreSQL 16 in the same VPC's private subnets** (ADR-008 — VPC-private, security-group ingress from ECS tasks only, RDS Proxy at launch), **S3 + CloudFront** for files/images (ADR-013), **Socket.IO + Redis on ElastiCache Valkey** for realtime (ADR-004). Every platform dependency is now **single-vendor AWS in `ca-central-1`** — one region, one jurisdiction, one bill; the former "RDS/Aurora as documented exit path" clause is discharged.

**Alternatives considered:** **Railway** (the previous decision) and **Fly.io** — lowest-ops PaaS, genuinely cheaper at pilot (~US$40–80/mo vs ~US$190–230/mo here) and faster to stand up, but neither runs platform compute in a Canadian region, leaving request processing outside Canada; serverless functions (can't hold WS/queues — ADR-004/012); EKS (orchestration ceremony a small team shouldn't buy). **The owner explicitly chose AWS**, accepting the higher cost and ops effort.

**Rationale:** (1) owner preference; (2) **full Canadian residency for both compute and data** — closes the open Q-11 residency concern and reduces the Law 25 cross-border-transfer analysis for the core platform to "none"; (3) enterprise credibility — AWS is the answer dealer-group and OEM procurement expects; (4) primitives already in stack (KMS) plus ALB/WAF/ACM/ECS are first-class, not add-ons.

**Consequences:** AWS costs more ops effort than PaaS — VPC/IAM/task definitions/scaling are now our code: **infrastructure as code (Terraform or CDK) in the monorepo, applied by CI**, is mandatory from day one. Honest pilot run-rate (2 API + 1 worker + 1 intake task, ALB, NAT, Valkey, WAF, edge): **~US$190/mo on x86, ~US$175 on ARM — budget US$180–230/mo** (Fargate ca-central-1 ≈ $0.04456/vCPU-hr + $0.004865/GB-hr x86; ALB ≈ $0.0247/hr + LCUs; NAT $0.05/hr + $0.05/GB; WAF $5/ACL + $1/rule-group + $0.60/M req; CloudFront's 1 TB/10M-req free tier makes SPA egress ≈ $0 at pilot). Deploys per ADR-023 (amended 2026-07-23): GitHub Actions → ECR → **ECS blue/green via CodeDeploy** — two ALB target groups per routed service, alarm-gated canary/linear traffic shifting, instant revert to the blue task set (`workers`, having no ALB target, keeps circuit-breaker task swaps). **Preview environments (the chosen approach): ephemeral ECS services behind the shared ALB via host-header rules** (`pr-{n}.preview.readyloans.app`, wildcard ACM cert) with SPA previews synced to a per-PR S3 prefix on a preview CloudFront distribution — created and destroyed by the PR workflow. Observability stack unchanged (ADR-025); **CloudWatch** becomes the AWS-native transport for infra logs/metrics (Fargate stdout → CloudWatch Logs, ALB/WAF metrics/alarms) while pino app logs continue to Better Stack.

**Amended 2026-07-23 (cost ramp):** the owner approved the budget but not full spend from day one. During the build phase, infrastructure runs a **minimal footprint**: smallest Fargate task sizes, a single API task acceptable pre-launch (the 2-task/2-AZ minimum applies from production launch), dev-tier services, single-instance dev/staging, and scale-to-zero wherever possible. The full production envelope (**~$650–$1,000/mo**) activates **only at production launch**; the US$180–230/mo AWS pilot figure above is the production-launch AWS core, not a build-phase entitlement.
**Amended 2026-07-24 (envelope restated for the RDS move):** the database line changes from Supabase ~$25–75/mo to **RDS ~$28–30/mo during build** (db.t4g.small Single-AZ staging + free local Docker dev — inside the old Supabase range, so the build-phase footprint is unchanged) and **~US$140–170/mo at production launch** (Multi-AZ db.t4g.medium ≈ $103 + RDS Proxy ≈ $23 + gp3 Multi-AZ 50–100 GB ≈ $13–25 + backup overage ≈ $0–5; all ca-central-1 on-demand). Net **+~$95–115/mo** at launch → the total production envelope is restated **~$750–$1,100/mo**; everything else in the ramp is unchanged.

## ADR-015: Encryption — TLS 1.3 everywhere; AES-256 at rest; field-level for PII

**Decision:** **In transit:** TLS 1.2 min / **1.3 preferred** on every hop — client→CDN, LB→app, app→Postgres (`sslmode=verify-full`), app→Valkey (TLS); HSTS + preload; automated cert issuance for tenant custom domains (ACM on CloudFront, ADR-014). **At rest:** AES-256 via **KMS-encrypted RDS gp3 volumes and SSE-KMS on S3** *(amended 2026-07-24 — was Supabase provider encryption)* as baseline; **field-level application encryption** for high-sensitivity fields — SIN, driver's licence number, date of birth, income/credit-app details, bank/void-cheque data — using **AES-256-GCM envelope encryption with AWS KMS** (per-tenant data keys), ciphertext in Postgres, **blind HMAC indexes** for equality lookup (phone/licence search). **pgsodium banned** (pending deprecation); pgcrypto acceptable for low-tier fields. Key rotation annually or on incident; decrypt paths audited.
**Rationale:** dealership credit apps are PIPEDA-sensitive/Law 25 material; encrypted columns can't be indexed directly — hence blind indexes. **Consequences:** PII fields are inaccessible to ad-hoc SQL; reporting uses derived non-PII aggregates.

## ADR-016: Validation — Zod 4, one schema source shared client/server

**Decision:** **Zod 4** is the single validation library. Domain schemas + all enums/status vocabularies live in `packages/schemas`; API request/response schemas in `packages/contracts` (ts-rest → OpenAPI); the SPA reuses the same schemas for forms (react-hook-form + zodResolver); workers validate job payloads with them; DB CHECK constraints are generated to mirror critical enums. Canadian-specific refinements standardized once: VIN (17 chars, no I/O/Q), postal code, phone normalization (E.164), `fr`/`en` language enum with **`fr` default**, cents-integer money type. `.passthrough()` on business payloads is banned.
**Rationale:** research + audit — validation exists but schemas are duplicated and permissive today. **Consequences:** a status or field added anywhere is added in exactly one place.
**Amended 2026-07-23 (VIN decode):** VIN *format* validation (above) is distinct from VIN *decoding*: production uses a **commercial Canadian-aware VIN decode service** (e.g., DataOne), selected by a short accuracy evaluation on Canadian-market vehicles; the free NHTSA vPIC API is a **development-only fallback** and is never used in production.

## ADR-017: UI system — shadcn/ui (Base UI) + Tailwind v4 + TanStack Table + shadcn Charts

**Decision:** **Tailwind CSS v4** + **shadcn/ui on Base UI primitives** (July 2026 default) vendored into `packages/ui` as the ReadyLoans design system (private registry). **TanStack Table v8** + the shadcn DataTable recipe for all grids (deal lists, lead queues, inventory); **AG Grid Enterprise (~$999/dev) deferred** until a concrete Excel-grade screen demands it. **shadcn Charts (Recharts)** for dashboards — CSS-variable themed, hence white-label-safe; Tremor blocks allowed for KPI shells. Adopted UX patterns from research: Pipedrive-style deal rotting, HubSpot 3-column record, Ctrl+K command palette, Salesforce path bar; light+dark themes via token swap.
**Alternatives:** MUI X (ecosystem clash), Untitled UI (React Aria — different primitive layer). **Consequences:** the legacy pages that bypass tokens (Desking/Accounting light-only) are rebuilt on tokens; no component ever hardcodes a brand color.
**Amended 2026-07-23 (Tailwind Plus removed; Stitch-first design selection):** the earlier "optional purchase: Tailwind Plus ($299 one-time)" is **decided against — not purchased**. The product is a **system** (a logged-in, data-dense CRM/DMS), not a landing page; template chrome adds no value here. Professional UI/UX remains **mandatory** and is delivered entirely by the free professional stack above (Tailwind v4 + shadcn/ui + design tokens). **New required step — design selection first:** before any UI code is written, the design direction, color palette, and UI style are selected using **Google Stitch** (AI design tool): Stitch generates candidate directions — driven via its **MCP server** (to be connected by the user; manual Stitch use in the browser is the fallback) — the owner picks one, and the chosen direction's palette/typography/style are translated into the locked design tokens in `packages/ui`, against which shadcn/ui is themed. Tokens are locked before UI build (roadmap step H-01); white-label runtime theming (ADR-018) is unaffected — Stitch selects the platform's default theme, tenant branding still overrides semantic tokens at runtime.

## ADR-018: White-labeling — runtime CSS variables from a tenant branding record

**Decision:** Single deployment, **runtime theming**: a `tenant_branding` record (logo + dark variant + favicon + email logo, OKLCH primary/accent/semantic colors, font (self-hosted WOFF2), radius/density, legal name, support contacts) resolved by **custom domain → subdomain (`{dealer}.readyloans.app`) → login org context**, injected as `:root` CSS variables before first paint (cached aggressively; neutral skeleton until loaded). Dark palettes **derived algorithmically** (OKLCH lightness transforms) with manual override. **WCAG AA contrast auto-validation** on tenant-supplied colors (auto-adjust foreground). A **parallel server-side branding path** feeds the same record into email templates and PDF generation (ADR-021/025) — hardcoded "Kia Mont-Laurier" branding anywhere is a release blocker.
**Rationale:** Tailwind v4/shadcn tokens make per-tenant theming zero-component-change. **Consequences:** every visual, email, PDF, SMS sender ID, and AI persona name is tenant-parameterized.

## ADR-019: i18n — react-i18next + i18next-icu, French-first (Bill 96)

**Decision:** Keep **react-i18next** and add **i18next-icu**; default locale **`fr-CA` per Quebec tenant** (detector order: user profile → tenant default → browser — fixes the current EN-default Bill 96 gap). `packages/i18n` holds shared EN/FR resources consumed by SPA, API (validation errors, notifications), workers (emails, SMS, PDFs — i18next on the server). **CI gate: EN↔FR key parity** (missing key = failed build) because Bill 96 requires the French UI be *equivalent*, including staff-facing SaaS. Money/dates via `Intl` (`fr-CA` → `1 234,56 $`). Contracts of adhesion: French presented first. Tailwind logical properties from day one (future RTL). AI agent converses FR-first for Quebec leads (area codes 438/514/450/819/873 + explicit preference question).
**Alternatives:** Lingui (PO workflow — revisit if outsourcing certified translation), next-intl (Next-only). **Consequences:** every string, enum label, email, PDF, and AI script ships in both languages or doesn't ship.

## ADR-020: Communications providers — Resend (email), Twilio (SMS/MMS + voice transport)

**Decision:** **Email:** **Resend** with **React Email** templates (tenant-branded via ADR-018, per-tenant sending domains/DKIM as tenants mature), Resend Inbound for ADF-email and delivery-photo intake. **SMS/MMS:** **Twilio Messaging** — one number per store, all client-facing SMS flows through the AI conversation layer (staff HIGH-urgency alerts are the only direct engine SMS), global STOP handling, CASL sender-ID footer. **Voice:** **Twilio ConversationRelay ($0.07/min, BYO-LLM over WebSocket)** so voice and SMS share one Claude brain and tool set; **Telnyx** (p95 118ms) documented as the latency/cost alternate if voice volume justifies a second telephony vendor. Quiet-hours engine enforced platform-wide in the send layer, not per feature, with **channel-scoped windows** (canonical table: `08-ai-automation/compliance-and-quality.md` §3): outbound voice follows the CRTC statutory window (9:00–21:30 weekdays / 10:00–18:00 weekends, recipient-local — no exemptions); AI-initiated SMS follows a platform-policy window (default 9:00–21:00 daily, per-tenant configurable); the SMS first-touch reply to a fresh inquiry is exempt by default (`first_touch_quiet_exempt`, tenant-disableable — disabled means first-touch defers to window start); replies to a live inbound client message are always allowed.
**Rationale:** already on Resend/Twilio; ConversationRelay keeps the single-brain architecture (ADR-022). **Consequences:** all sends go through BullMQ (idempotent, logged, consent-checked); no route handler calls a provider SDK directly.

## ADR-021: Documents/PDF — HTML templates rendered via headless Chromium

**Decision:** Replace direct PDFKit composition with **HTML/CSS templates (React → HTML) rendered to PDF by headless Chromium (Playwright)** in sandboxed BullMQ workers; ExcelJS stays for spreadsheets. Templates consume the tenant branding record and i18n resources (FR-first documents, Bill 96 contract rules). Generated documents are **immutable snapshots**: the bill-of-sale payload is persisted at generation time (audit finding: BoS never persisted, localStorage-only) with a hash, stored in the documents bucket.
**Alternatives:** keep PDFKit (imperative layout makes white-label/i18n templating painful). **Consequences:** one template system for the 13-document catalog; wet-ink/e-sign lifecycle tracking is data, not rendering.

## ADR-022: AI lead-automation stack — Claude API, tool-use workflow, compliance-gated

**Decision:** **LLM:** Anthropic Claude API — **Claude Opus 4.8 (`claude-opus-4-8`)** for conversation (SMS + voice, shared system prompt core), **Claude Haiku 4.5** for per-turn structured extraction and classification. **Patterns:** stateless Messages API + **tool runner** with a small audited 7-tool set (`lookup_inventory`, `check_agent_availability`, `book_appointment`, `create_or_update_lead`, `request_human`, `send_credit_app_link`, `record_consent` — the last captures the server-verified express-consent "YES/OUI" reply that the ADAD gate below requires); **structured outputs** (JSON schema, `additionalProperties:false`) for CRM field extraction; **prompt caching** on the frozen per-tenant prefix (dealership config, compliance footer, inventory summary) — ~90% input-cost cut; conversation history in Postgres. **Voice:** ConversationRelay streaming to the same agent (ADR-020). **Routing:** deterministic rules (language, availability/presence, load, ad-spend distribution tallies) + model-assisted scoring; any financing-significant automated decision carries **Law 25 s.12.1 disclosure + human-review path**. **Compliance engine (platform-level, non-optional):** per-lead consent ledger (express/implied, source, timestamp, 6/24-month expiry), immediate global STOP, quiet hours, DNCL scrub (≤31-day freshness) + per-tenant internal DNC, **no automated outbound solicitation calls without recorded express consent (ADAD)** — "Can our assistant call you? Reply YES" captured in SMS, AI self-identification in first turn (FR+EN), full conversation audit logs. Guardrails: agent never quotes pricing/rates/approval odds; max 3 vehicles via MMS.
**Alternatives:** ElevenLabs Agents/Retell/Vapi (managed but a second brain + per-min premium); OpenAI Realtime (competing model stack). **Consequences:** `packages/ai` owns prompts/tools/evals; per-tenant AI usage metered for billing (ADR-024).
**Amended 2026-07-23 (model-agnostic AI):** the AI layer is **model-agnostic by design**. Opus 4.8 (conversation) and Haiku 4.5 (extraction) are **launch defaults, not hardcoded choices**: `packages/ai` includes a **built-in evaluation/A-B harness** run across candidate models (Claude Opus/Sonnet/Haiku and future models) per task, and the platform selects the **best quality-per-dollar model per task**. Model assignments are configuration — **swappable per tenant and per task without code changes** — and re-evaluated as new models ship.
**Amended 2026-07-23 (AI error assistant):** the same model-agnostic layer powers a built-in **AI error assistant** for platform operations: when production errors occur it auto-reports — aggregating the Sentry issue, trace, and recent releases — and produces a plain-language description, probable cause, and suggested fix; it files/updates an internal ops ticket (keyed by Sentry issue, deduplicated) and surfaces the guidance in the **admin console ops inbox**, with a "was this helpful" feedback loop feeding the eval harness. It also powers an in-app **"describe this screen / guide me"** helper for admins. Constraints: **least-privilege, read-only** access to observability data (already PII-scrubbed by construction — ADR-025); no secrets/PII in prompts; output is **suggestions only, never auto-executed fixes**; **admin-facing only** — end users continue to receive generic error messages (04-security/api-security.md §11). Spec: 07-infrastructure/observability.md §12; FR-AI-020/021.

## ADR-023: CI/CD & environments — GitHub Actions; dev → staging → prod

**Decision:** **GitHub Actions**: lint (eslint+prettier), typecheck, unit tests (Vitest — desking/tax/commission math in `packages/core` requires ≥90% coverage), contract/OpenAPI generation check, i18n parity gate (ADR-019), migration dry-run against **ephemeral Postgres containers (testcontainers) in CI** — with **staging RDS snapshot-restore rehearsals** for risky/destructive schema changes *(amended 2026-07-24 — replaces Supabase branch/preview databases with the Supabase exit, ADR-008)*, Playwright smoke E2E. **Environments:** `dev` (local Docker Postgres via compose), `staging` (own **db.t4g.small Single-AZ RDS instance** + separate AWS account/ECS cluster, seeded synthetic tenants), `prod` (Multi-AZ RDS per ADR-008). Per-PR preview environments per ADR-014 (ephemeral ECS services behind ALB host-header rules + per-PR S3/CloudFront SPA previews); on merge to `main`: SPA and service images built and deployed per the blue-green amendment below (GitHub Actions authenticates to AWS via OIDC — no long-lived AWS keys); migrations applied by CI before app rollout (expand-and-contract pattern for breaking schema changes). Secrets in platform secret stores only — **no keys in the repo** (audit found live service-role/Resend keys in tree; rotation is a Phase 0 task).
**Consequences:** no manual deploys; every prod change is a PR.
**Amended 2026-07-23 (blue-green deploys):** production deployments are **blue-green with instant revert** — the original "ECS rolling deploy with circuit breaker; CodeDeploy blue/green as optional later hardening" default is superseded. **Services:** ECS blue/green via **CodeDeploy** — each ALB-fronted service (`api`, `intake`) owns **two ALB target groups**; the green task set is health-gated (`/healthz` + `/readyz`), traffic is shifted **canary or linear** (config-selectable), and **CloudWatch alarms trigger automatic rollback** — traffic snaps back to the blue task set in seconds, with blue retained 1 hour post-cutover for instant revert; `workers` (no ALB target) keeps circuit-breaker task swaps with previous-revision redeploy as rollback. **SPA:** **versioned S3/CloudFront releases** — immutable per-SHA prefixes with the active release selected by a pointer; **rollback = pointer flip + invalidation**, instant, no rebuild. **Migration gating is unchanged:** expand-and-contract (ci-cd.md §6) already guarantees the blue and green versions run correctly on the same schema while both serve traffic. Detail: 07-infrastructure/ci-cd.md §7–8, hosting-topology.md §5.

## ADR-024: Tenant billing — Stripe Billing with usage-based metering

**Decision:** **Stripe Billing**: per-rooftop (store) monthly subscription tiers (target wedge $300–$800/mo vs quote-only incumbents) + **usage-based meters** for AI voice minutes, SMS segments, and AI conversations (Stripe Meters API), 14-day trial, Stripe Tax for GST/QST/HST on invoices, customer portal for self-serve payment management. Entitlements (seats, stores, AI quotas, feature flags) derived from the subscription and cached on the tenant record; rate limits (ADR-011) read the same quotas. Dunning → grace period → read-only mode (never hard data deletion).
**Alternatives:** Paddle (MoR, less metering flexibility), homegrown invoicing. **Consequences:** billing events consumed via signed Stripe webhooks into `apps/api`; pay-per-appointment upsell (Numa-style) expressible as a metered price later.
**Amended 2026-07-23 (admin-managed pricing):** subscription plans, prices, and entitlements are **fully manageable from the platform admin console** — create/edit/reprice plans, per-tenant overrides, and grandfathering of existing subscribers on their current terms. **Stripe products/prices are created and updated through the admin UI** (via the Stripe API), never hand-edited in the Stripe dashboard or hardcoded. **Pricing is data, not code**: a price change is an admin operation, not a deploy.

## ADR-025: Observability — Sentry + PostHog + OpenTelemetry + pino + Better Stack

**Decision:** **Sentry** (SaaS, Team plan): errors + tracing + release health, frontend and backend, PII scrubbed via beforeSend, no request bodies with personal data. **PostHog (EU cloud)**: product analytics, session replay (input-masked), feature flags, experiments — **consent-gated** (`opt_in_capturing` only after Law 25 granular opt-in). **OpenTelemetry** SDK + auto-instrumentation on Fastify/BullMQ/pg so backends stay vendor-portable; trace context propagated through jobs. **pino** structured JSON logs (tenant_id, request_id, actor) shipped to Better Stack Logs; **Better Stack** uptime monitors + public status page. SLOs: API p95 < 300ms, lead-intake ACK p99 < 1s, AI first-touch < 60s — alerting on burn rates.
**Consequences:** every request/job carries tenant + trace IDs; speed-to-lead metrics are first-class product telemetry, not just ops data.

## ADR-026: Migration strategy — strangler rebuild, feature logic preserved, clean-start data

**Decision:** Greenfield monorepo (ADR-001) implementing this stack; the existing app is the **reference implementation for business rules** (desking math, tax tables, commission plans, pipeline/checklist rules — the 7/10 asset), ported into `packages/core` with tests before any UI. Build order: tenancy+auth+RLS foundation → core schema (cents, real FKs, single status vocabularies) → module parity (pipeline, desking, inventory, delivery) → clean-database launch with Kia ML onboarded as tenant #1 → AI lead layer. **No new features land on the legacy codebase.** Timeline expectation per audit: 2–3 months to secure single-tenant parity, 4–6 months to multi-tenant SaaS.
**Amended 2026-07-23 (clean start — no data migration):** the owner confirmed **all legacy data is test data** with no production value, and **none of it is migrated**. There is no ETL, no historical commission reconciliation, no dual-run week, and no read-only-legacy transition period; the earlier "data migration from the live tracker" step is dropped. Production launches with a **clean, empty database plus seed/reference configuration** (provinces, tax profiles, status vocabularies, document templates). Commission plans and store configuration are **entered fresh at tenant onboarding** and validated against the legacy code's rules. The legacy system remains a **business-rules reference only** — its code and specs define the rules; its data is worthless — and the Express app is shut down once Phase 1 parity is signed off.
**Consequences:** downstream build-plan documents must sequence against this order; any conflict between an old spec and these ADRs resolves in favor of the ADR; any remaining reference to migrating, reconciling, or dual-running legacy data is void.
